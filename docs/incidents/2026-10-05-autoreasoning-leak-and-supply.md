# 2026-10-05 · cc-ft 报「auto:reasoning 不存在」——挖出供给面的三条断链

> **一句话**：用户报的是一句**客户端**的报错，查下去发现网关**三条独立的断链**——
> 上游的 404 认不出、403 不换 key、供给面是份手写白名单还只增不减。
> 三处断的都不是"能力"，是**"看得见"**。
>
> 现场：用户在使用中撞上（cc-ft 会话）· 由用户报错发现
> 相关提交：本仓分支 `feat/supply-hardening`（`b8dde26`…`674865a`）
> 相关任务：`T-031`…`T-038`

---

## 0. 三十秒版

| | |
|---|---|
| **症状** | cc-ft 会话弹「There's an issue with the selected model (**auto:reasoning**). It may not exist or you may not have access to it. Run /model…」 |
| **断链一** | 上游对**已退役模型**回的规范 404（`not_found_error`）**没被网关认出** ⇒ 该候选就地终止、404 **原样透传** ⇒ 客户端按**自己配置的模型名**（`auto:reasoning`）渲染成"模型不存在"。而服务端退的是 `minimax/minimax-m3:free`——**一个用户从没打过的名字**（T-031/T-032） |
| **断链二** | **403 被当"模型级"事实** ⇒ 只换模型、**绝不换 key** ⇒ 抽到无权限的那把 key 就白扔半个池子。受控实验：同一模型 **4 把 key 200 / 4 把 403**（T-035）。真身：修前 ~50% → 修后 **8/8** |
| **断链三** | 供给面是**人手写的平台白名单**（2 个平台），且**只增不减、从不复核**；纳新**永远不会发现一个新平台**（`for i := range cfg.Providers`）（T-033/T-036/T-037） |
| **一句话** | **不是"没有活模型"，是"网关看不见手里的活模型"。** 三处都断在"看得见"上 |
| **最可迁移的教训** | 判据可以"宁窄勿宽"，但**窄要窄在措辞，不能窄在结构**——结构化字段（`error.type`）才是可靠判据；靠词表认形状，那天上游换个说法就全瞎 |

## 1. 现场（判据，非推断）

`/decisions`（400 条窗口）：

```
auto:reasoning | agnes-anthropic | 200 | model= agnes-2.5-flash    ×336
auto:reasoning | xkiro-anthropic | 404 | model= minimax/minimax-m3:free  ×3   （retried=true, elapsed 102–115s）
auto:reasoning | router          | 503 | exhausted anthropic candidates (tried 2, limit 4)  ×20
```

`/doctor`：60 分钟 365 请求、失败 23（**6.3%**）——≈ agnes-anthropic 自身的抖动率。

**这组里最值钱的一条**：客户端说的是 `auto:reasoning`，服务端说的是 `minimax/minimax-m3:free`。
⇒ **客户端显示的模型名是它自己配置的那个**，不是服务器回的。
⇒ 凡是"模型不存在"类的答复，用户看到的永远是**自己填的名字**——而这个名字是我们设计的抽象，
他根本无从"改一行"。

## 2. 定位路径（可复用）

1. **别信第一印象**：报错措辞是客户端的，先分清"谁在说话"（这条定了整整一下午的方向）。
2. **读决策留痕的字段而不是聚合**：`provider_id` + `model` + `status` 三个字段就指出了 xkiro-anthropic。
3. **对照实验**：上游不认 key 与上游没收到 key，**401 的文案不一样**
   （`Invalid token` vs `Missing or invalid API key`）——一句话就分辨"key 送了没"。
4. **容器内直测**：宿主对某些上游有 TLS 中间人（`x509: unknown authority`），
   而容器出网干净 ⇒ 把测量搬进容器，别在宿主上跟证书缠斗。
5. **先证伪自己**：见 §8.2。

## 3. 根因（第一性）

### 3.1 404 认不出 ⇒ 就地终止（`tryCandidate`）

```go
if fail.Kind == provider.FailNone && res.StatusCode == 404 && mi+1 < len(models) {
    break                              // 还有下一个模型 → 换
}
return res, fail, true, m              // 没有下一个模型 → done=true，404 当"完成态"上抛
```

而**认出**的 404（`FailModelNotFound`）走的是另一句：

```go
if mi+1 < len(models) { break }
return res, fail, false, m             // done=FALSE → 沿候选链继续
```

**同一个 404，两条路，只差 body 能不能被认出。** 缺陷出在后者——
认不出 ⇒ `done=true` ⇒ 透传 ⇒ 客户端按自己的模型名报错。

而 `isModelNotFound` 的 marker **全是 OpenAI 味措辞**
（`does not exist` / `unknown model` / `model not found` …），
**不含 Anthropic 规范的 `not_found_error` 形状**——恰好是 Anthropic 协议端点最常吐的那一种。

### 3.2 403 只换模型不换 key

2026-09-20 的结论是"403 = 账号对这个模型没权限，凭据是好的" ⇒ **不惩罚 key**。
那句**"不惩罚"是对的**（长禁 key 会把整层下线一小时）；但它顺带把"**换一把再试**"也一并省了。
受控实验（直打 `api.xkiro.com`，同一模型 `qwen/qwen3-max:free`）：

| key | 状态 |
|---|---|
| aimlying / iphone / meimei / zhengying | **200** |
| 76690315 / aifengguo / aimlying2 / lxjfordream | **403** |
| cc-xkiro | 429（当日额度） |

⇒ **403 在 xkiro 上是 key 级事实**。"403 与凭据无关"这条**只对某些上游成立**，
而它被当成了普适规律写进了路由。

### 3.3 供给面：手写白名单 + 只增不减

- `catalog.Harvester` 只对 **`cfg.Providers`** 发现新**模型** ⇒ **永远发现不了新平台**。
  池子大小 = 人手写的常数（当时 2 个），vault 里有几个平台都白搭。
- `MergeAuto` **只追加、永不删**；纳新 `Known` 跳过已在册的 id ⇒ **死了也发现不了**。
- 实测腐化速度：xkiro 纳新 25 个模型，**12 小时内 6 个（24%）**被上游撤掉。

## 6. 牵出的问题（修一层露一层）

1. **"严格准入"会把池子清空**——ADR-004 早就预警过（"最好的模型只有 4/5"），
   本次实测复现：OpenRouter 免费模型天花板 **4/5（80%）**，按 100% 的线**一个都进不来**。
   最终由用户定线 **3/5**。
2. **免费档按账号限流是真约束**——OpenRouter **50 次/天/账号**，一轮十题题组就把当天额度打满。
3. **一批 key 已经死了**——`unorouter` / `orcarouter` 各 10 把，**20/20 回 401 `Invalid token`**
   （是"平台不认"而不是"额度用尽"；后者是 429）。
4. **不是所有平台都能被自动发现**——Cloudflare 的 `/ai/v1/models` 回 **405**（端点不支持列模型），
   自动纳新对它无效，得手写模型名。
5. **纳新不会发现新平台**——见 §3.3；T-037 只做"对账/报缺"，接线仍要人工。

## 7. 沉淀下来的原则

| # | 原则 | 出处 |
|---|---|---|
| 1 | **判据宁窄勿宽，但"窄"要窄在措辞、不能窄在结构**。`error.type` 是结构化字段，比任何词表都可靠；靠词表认形状，上游换个说法就全瞎 | §3.1 |
| 2 | **结论必须带"对谁成立"**。"403 与凭据无关"**对某些上游成立**，被当成普适规律写进路由后，白扔半个 key 池 | §3.2 |
| 3 | **"不惩罚"不等于"不重试"**。当年为防长禁 key 而删掉的动作里，混进了"换一把再试"——两件事被一起删了 | §3.2 |
| 4 | **循环找活模型的前提是池子里有活的，且看得见**。供给面的三条断链（认不出 / 不换 / 发现不了）全在"看得见"上 | §3 全节 |
| 5 | **手写白名单 + 只增不减 = 单调腐化**。供给是易腐资源，没有淘汰机制就只会烂下去 | §3.3 |
| 6 | **静态断言覆盖不了活供给**。`-check` 查的是"配置声明的覆盖"，配置烂成墓地它照样绿 | §6.4 |
| 7 | **客户端显示的模型名是它自己配置的**——凡是"模型不存在"类的答复，用户看到的永远是我们给的抽象名，他无从"改一行" | §1 |

## 8. 方法（比结论耐用）

### 8.1 三种实验

| 方法 | 用在哪 | 要点 |
|---|---|---|
| **受控实验** | 403 到底是不是 key 级 | 固定模型、**只换 key**，看状态分布——一把一结论不成立，**分布**才成立 |
| **对照实验** | key 送了没 | 不带 key 与带 key 的 401 **文案不同** ⇒ 证明 key 确实送达、是平台拒绝 |
| **变异检验** | 每条回归测试 | 把新代码停掉，确认测试**变红**且症状与现场一致。没做过的回归测试等于没写 |

### 8.2 先证伪自己（本次走了两趟弯路）

这个案子里我**两次改了结论**：

1. 先判"网关认不出 Anthropic 形状 ⇒ 不轮换"；
2. 写了个测试**当场变绿**，据此**推翻自己**，改判"根因是供给（没得换）"；
3. 对照实验（同场景只换 body 措辞）证明**第 1 判是对的**——第 2 步那条测试只是**没走到边界**。

**教训**：一条测试"没红"不等于假设被证伪，可能只是**没踩到那个分支**。
边界要**单独构造**，不能指望随手写的用例恰好落在上面。
