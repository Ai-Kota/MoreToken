## 四项

### 1. 配置缺陷（已确证，T-009 我自己引入的）

`config/config.json` 的 `agnes` provider：
- `keys` = 33 把 agnes **+ 11 把 xkiro** 混在一个池
- `models` 含 xkiro 的 `deepseek/deepseek-v4-flash`
- 但 `base_url` 是 `https://apihub.agnes-ai.com/v1`（agnes 的端点）

**实测**：xkiro 的 key 打 agnes 端点 → **401 `Invalid token`**；agnes 的 key 打 agnes 端点 → 200。

后果：池内 **11/44（25%）必然失败**。T-009 加的 I9（401 隔离）让它们被长禁 1h 后放回，
于是每小时白撞 11 次，且每 4 个请求就有 1 个多一次无效上游调用。

根因：把两个**不同 base_url** 的 provider 合并成了一个（图省事）。修法：拆回两个 provider。

### 2. 探测缺陷（T-009 发现，未修）

`main.go` 的 `firstRealKey(p)` **永远取配置里第一把 key**，且不看池的冷却状态。
而 `state.ProbeFree` 要求**所有** free provider 健康才算（遇失败即 break）。

串起来：**第一把 key 一旦失效 → 每 30s 的探测永远失败 → 健康窗口永远累积不到 3 分钟
→ 一旦进了付费层就再也回不到免费**，哪怕其余 32 把全是好的。现在是运气不是设计。

修法：探测改为在真实 key 里**轮转换 key**（起点每轮推进），命中任意一把即视为该 provider 健康。

### 3. kinds 实测（此前是我按印象填的）

`kinds` 现在是我"按已知事实保守填"的——agnes-2.0-flash 我根本没测过就标了 general/fast。
类型路由的正确性建立在这个声明上，声明不能是猜的。

修法：对每个 distinct 模型跑**可判定的能力探针**（推理题 / 编码题 / 常识），按结果定 kinds，
并把实测证据记进文档；`fast` 用实测延迟分档。

### 实测记录（2026-09-19）

**配置缺陷**：xkiro 的 key 打 agnes 端点 → `401 Invalid token`；agnes 的 key → 200。
拆分为 6 个 provider 后 `/health` 每池各持自己的账号（33/11/33/11/1/1）。

**探测缺陷**：改为轮换取 key（`internal/probe`），并把逻辑提成独立包
（`test-all.sh` 只跑 `./internal/...`，留在 main 里等于没有回归覆盖）。

**kinds 实测**：6 模型 × 5 题 × 4 样本 + 火车题 10 样本。结论——
- `coding`/`general` **不区分**（全员 88–100%）→ 声明为普遍能力，**不再声称是区分性类型**
- `reasoning` 区分，但只有极端值可信（10/10 与 0/10）；中间区不足以支撑声明
- `fast` 仅对有延迟实测的 agnes 三模型声明
- 反直觉发现：付费的 agnes-3.0-flash 推理最差（0/10）却最快，它不是"更强"而是"不做长推理"

**Claude Code 实接**：

### 计划外发现（已在 MODEL-CAPABILITY.md 记录）

并发压测（120 请求/25s ≈ 720 RPM，超过 33 账号 × 20 RPM ≈ 660 RPM 的池容量）把全部 key
打进 429 冷却。观察到：免费全挂 → 状态机正确触发 `all-free-unavailable` → 切付费并返回 200；
冷却 60s 后自动恢复；期间返回 503 而非误透传 401。
**短板**：付费层只有 1 把 key，同样会被打冷却——兜底是"保命"不是"扩容"。

## 注意

- 能力探针要**可判定**（有唯一正确答案），不用"看起来不错"这类主观判断
- 探针走网关本身（Go net/http），避开本机 curl 对 agnes 的 schannel 间歇失败
- 实测证据写进 `docs/quality/` 而不是只留结论——下次换模型时要有据可依
