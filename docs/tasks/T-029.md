# T-029: Docker 部署通用化——两种形态成为一等公民（generic / vault）

> 起因：2026-09-29 用户第一性原理评估后定性——**docker 部署与本地直跑将是别人使用的
> 两种重要方式**。现状 docker/ 是"本机专用"：compose 硬编码 bridge.creds 绝对路径、
> mt-deploy 强依赖 vault materialize、mt-verify 硬编码宿主工具路径。别人克隆仓库后
> **跑不起来**。本任务把 docker 形态拆成两条自包含路径。

**允许修改文件**：docker/**, docs/**, config/**, .gitignore, QUICKSTART.md

## 第一性分析结论（本任务的依据，全文见会话记录）

- 功能面差异 = 0（同一份代码、同套验证矩阵两形态全过）；差异全在**运行时边界**
- 真正的变量是二维矩阵：**密钥来源（字面量/env: vs vault:）× 部署形态（本地 vs docker）**
- materialize 管道/命名卷/变更检测的全部复杂度 = "vault+docker"一格的代价（本机独有）
- **一般用户（env:/字面量 key）走 docker 无任何安全折损**（key 本来就在磁盘 .env 里），
  白拿自愈/可复制/跨平台 → generic 路径应是对外默认推荐

## 设计决策（定死，不摇摆）

| 争议点 | 决定 | 理由 |
|--------|------|------|
| 一个 compose + override 合并？ | **两个自包含 compose 文件** | 同挂载点（/run/moretoken/config.json）在 override 合并时"文件 bind vs 命名卷目录"语义歧义；基建文件的重复比巧妙合并的脆弱便宜 |
| generic 的 config 来源 | **单文件 ro bind**（`../config/config.json`，可 MT_CONFIG 覆盖） | config 只在启动时读一次、无热加载 → 无 T-026 S1 的 inode 钉死问题（那只影响运行中被 rename 重写的 tokens.json） |
| generic 的 key 注入 | compose `env_file: .env.keys`（required:false）→ 容器内 ResolveKeys 解析 `env:` | 复用既有已测试代码路径，容器内零新增机制；文件缺失=字面量 key 用户不受影响 |
| NATS | **只在 vault 形态**（本机）；generic 文档说明可选 env 三件套 | 一般人没有 NATS 服务器；发布器本就缺失即 no-op |
| 多实例 | base compose 参数化 `MT_CONTAINER`/`MT_PORT`/`MT_CONFIG`（默认 moretoken/8462） | 测试 generic 形态时可 :8477 旁路起，不动生产容器；用户也可多实例 |
| generic 的 token 发放 | `mt-token.sh`（one-shot 容器 `--entrypoint moretoken`，挂 runtime rw） | 容器内有 linux 二进制、-token-plain 零 vault 依赖；宿主无需 Go 工具链 |

## 交付物

1. **docker/docker-compose.yml**（重写 = generic 形态）：build 同上；`${MT_CONFIG:-../config/config.json}:/run/moretoken/config.json:ro` 单文件 bind；`./runtime:/run/mt-tokens:ro`；`env_file: [{path: .env.keys, required: false}]`；`container_name: ${MT_CONTAINER:-moretoken}`；ports `127.0.0.1:${MT_PORT:-8462}:8462`；其余安全卫生照旧（read_only/tmpfs/no-new-privileges/healthcheck/logging/restart:always）
2. **docker/docker-compose.vault.yml**（新 = 本机形态，现 docker-compose.yml 原样迁入）：命名卷 external + NATS creds + TOUCH=off；mt-deploy.sh 改 `-f docker-compose.vault.yml`
3. **docker/mt-up.sh**（新 = generic 部署）：pre-flight（docker 在、config 在——缺则指路 `cp config.example.json config.json`、runtime/tokens.json 缺则建空名单+响亮提示"当前无鉴权仅回环"）→ `compose up -d --build` → 轻量健康检查 → 指路下一步（发 token 命令/看日志找 unresolved WARN）
4. **docker/mt-token.sh**（新 = generic token 管理）：`gen|list|revoke|rotate` 子命令经 one-shot 容器操作 runtime/tokens.json（Linux 宿主自动带 `--user $(id -u):$(id -g)`）
5. **docker/mt-verify.sh 参数化**：`MT_CONTAINER`/`MT_BASE`/`HOST_BIN`/`NATS_BIN_HOST` 环境变量可覆盖（默认=本机现值，本机行为零变化）
6. **docker/.env.keys.example**（新）+ **.gitignore 加 `docker/.env.keys`**（明文 key 文件绝不入库）
7. **README/QUICKSTART 双路径重写**：generic=默认推荐（克隆→cp config→.env.keys→mt-up.sh 三步），vault=本机形态（现文档迁入）；NATS 可选说明；token 双姿势
8. 既有 vault 链路**零回归**：mt-deploy（vault.yml）SAME 路径实测、生产容器不断

## 实测教训（新增一条入 README 排障表）

**Git Bash MSYS 路径转换**：`docker run … -tokens-file /rt/tokens.json` 里
`/rt/...` 被 MSYS 转成 `D:/Git/rt/...` 传进容器 → `mkdir D:: permission denied`。
修正：挂载源 `cygpath -m` 显式 Windows 形态 + `MSYS_NO_PATHCONV=1` 关其余参数转换
（Linux 忽略该变量，跨平台安全）。mt-token.sh 与 mt-verify.sh container 通道都已修，
generic 形态 token 全链重测通过。
