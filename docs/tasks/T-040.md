# T-040: key 级 429 日账本——当日额度耗尽的 key 摘出，不再全天撞墙

> 用户定性（2026-10-07）：**"日常任务 100% 压免费池"**——持久化任务跑得越久，
> "429 当日摘除"比"60s 短冷却"更救命。今日实测：xkiro 27 模型全 429（日额度耗尽）、
> agnes 换 key 全 429（账号级墙）——60s 冷却对"今天没了"没有意义。
>
> **状态：✅ 已完成并验证（2026-10-07）。** 验证记录见文末「验证」。

**前置证据**：
- `internal/pool/pool.go:106-116`：429 → `RecordRateLimit` 60s 短冷却，**撞两次只刷新不升级**；全仓无日级记账（调研 B 全仓搜 `quota/日账本` 零命中）。
- `TEST/model-evaluator/admitted.json` 上游 429 原文自证日额度现实（xkiro："reached today's free-model token quota … wait for the daily reset"）。

## 交付

**KeyLedger（新文件 internal/pool/ledger.go，与 pool 同包）**：
- 结构：`map[keyID]{day string; count int; lastAt time.Time}`，时钟可注入（fake clock 测试，与 pool_test.go 的 bench 模式同型）。
- **记**：Router 在现有 `RecordRateLimit` 调用点（router.go:574-577）同步记 ledger：当日 429 计数 +1。
- **用**：Router Select key 时（router.go:545 附近）：该 key 当日 count ≥ N（N 可配，默认 4）⇒ 视同池级退避跳过该 key 至**当日 24:00 重置**（跨日自动解锁，无需人工）。
- 持久化：**不做**（保持内存态，与 pool 的冷却同寿命；重启清零是安全方向——宁可多试一次，不宁可永久封死）。auth.Store 的异步回写模式留给将来真需要跨重启再上。
- 可见性：`/doctor` 不加新字段（最小改动），ledger 状态进 `/decisions` 的 reason（跳过的 key 记 `skipped_daily_quota`，与 T-020 的 `skipped_backoff` 同类单独可辨）。

**为什么 N=4**：单次 429 常是"这一分钟池子撞墙"的余波；连续 4 次 429（60s 冷却间隔）≈ 该账号当日额度真的见了底。宁可略晚摘除（晚 3 次 × 60s ≈ 3 分钟损失），不可误杀当天还有额度的 key。N 做成 config 字段 `rate_limit_daily_ban`（缺省 4），0=关。
