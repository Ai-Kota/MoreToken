## 缺口（实测判据）

现有的 503 留痕只有**聚合**：

```

```

**它回答不了"是谁坏的、怎么坏的"。**

**但那是【推断】**：当时的留痕一个字都没记谁失败了，所以这个问题**至今无法回答**。

## 两层证据丢失（都亲身经历过）

   **08:21 那次的现场被我亲手抹了**。这正是 `T-017` 说的那件事。

## 改了什么

### `router.Attempt` —— 逐个候选的失败留痕

```json
{"provider":"agnes-anthropic","model":"agnes-2.5-flash",
 "kind":"transport","status":0,"reason":"transport: dial tcp: ..."}
```

- `kind` 取 `provider.FailKind` 的**稳定短名**（`transport`/`upstream`/`ratelimit`/
  `auth`/`denied`/`stream_mid`）。**是契约**：改名会断掉基于历史留痕的统计。
- **`skipped_backoff` 单独一类**：池级退避中被跳过 ⇒ **一次请求都没发**。
  它和"发了但失败"是两件事，混在一起会把"自我保护"读成"试了没用"
  —— 这是 `555e60c` 那条教训（退避不是可用性证据）在留痕层面的同一件事。
- 成功路径**不带**留痕（别拿噪音淹没日志）。

### 接线

`Route` 在失败时也返回带 `Attempts` 的 `Result`（错误路径原来是裸 `Result{}`），
proxy 的 503 分支把它写进决策日志。**改动很小，因为 proxy 已经拿到了 `res`。**

## 🔴 上线 3.5 小时后，第一次查数据就抓出一个**正在生产的 bug**（2026-09-21 14:00）

**这个 bug 是我自己引入的**，而且已经在线跑了两小时。

### 症状

```
29 × 503 / 2 小时（12:01–13:58，**均匀滴漏**，约每 4 分钟一条）
├─ 23 ×  "router: no anthropic provider offers kind \"any\""   ← want=auto（不带类型）
└─  6 ×  "exhausted ... (tried 2/3, limit 4)"                  ← 真·候选失败
```

### 根因

接指标时，为了让维度有个显示名，我**就地改了 `wantKind`**：

```go
wantKind, virtual := router.ParseVirtual(probe.Model)
if virtual {
    if wantKind == "" {
        wantKind = "any"          // ← 为指标标签而改
    }
    kindLabel = string(format) + "/" + wantKind
}
// …而 wantKind 同时是下面这行的参数：
WantKind: wantKind,               // ← 于是 `auto` 被当成"要求 kind=any"
```

**没有任何 provider 持有 `any` 这个 kind ⇒ 候选为空 ⇒ 503。**

### 为什么它特别值得记

**它的聚合原因看起来像"配置缺失"，完全看不出是网关自己造的。**
`no anthropic provider offers kind "any"` —— 读日志的人会去翻 config，
而真相是一行赋值。

这正是 `T-020` 存在的理由：**修之前，这个问题查不出来。**

### 修法

标签用**单独的变量**算，绝不就地改路由参数：

```go
label := wantKind
if label == "" { label = "any" }   // 仅显示用
kindLabel = string(format) + "/" + label
```

### 验证

- 回归测试 `TestEndpoint_PlainAuto_NotTurnedIntoKindAny`（两种格式都覆盖）
- **变异检验**：把 `label` 改回 `wantKind = "any"` ⇒ 测试逐字报出生产错误
  `router: no anthropic provider offers kind "any"`
- 生产实测：`{"model":"auto"}` → **200**，落 `agnes-anthropic / agnes-2.5-flash`

### 另一条被这次数据顺带证实的线索

6 条真·候选失败里，**全部 8 次 transport 的原因都是 `context canceled`**
——**不是网络、不是上游，是调用方主动断开**。

结合之前看到的 `avg_ms ≈ 15s`，指向一个具体机制：**请求太慢 → 客户端等不及断开 →
网关在途的上游调用被取消 → 被记成"候选失败" → 池级退避 + 触发降级**。

也就是说：**用户取消一次慢请求，会让网关惩罚 provider 60 秒**。
若连续几次，就可能把整层推进"全池耗尽"。这解释了早先那次"同一秒 7 条一起挂"
（上下文一死，后续候选**瞬间**全失败）。
