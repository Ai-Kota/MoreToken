# T-023: 声明上下文窗口（`/v1/models` 的 `max_input_tokens`）

> 起因：2026-09-22 某会话堆到 **994166 token**，而模型上限 524288 ⇒ 卡死循环。
> 用户定性：**"无感 ≠ 不报错；无感 = 报得准。"** 更根本的是——**根本不该产生这种请求。**

**允许修改文件**：internal/**, main.go, docs/**, config/**

## 判据（来自 Claude Code 二进制，不是猜的）

本机 `claude.exe`（248MB）里嵌着 Anthropic 的 API 文档：

> Each model object has `id`, `display_name`, `created_at`, and — since Mar 2026 —
> **`max_input_tokens`** (the context window), `max_tokens` (the output cap), and `capabilities`.
> **There is no `context_window` field.**

**而我们的 `/v1/models` 一个都没给** —— 客户端拿不到窗口，于是按它自己的假设决定何时压缩，
一路堆到 99 万。

## 窗口的取值来源（全部是证据）

| 模型 | 窗口 | 来源 |
|---|---|---|
| agnes-2.5-flash / 2.0-flash / 3.0-flash | **524288** | **实测**——发一条超限请求，读它自己报错里的 `(524288 tokens)` |
| xkiro 各模型 | 1000000 / 1048576 等 | 上游目录直接给 `context_length`，**纳新自动带回** |

**不猜**：上游不给、也没实测过的，留空 ⇒ `/v1/models` 里不出现该字段 ⇒ 客户端退回它自己的默认假设。

## 设计

1. `config.Model` 加 `context_length` / `max_output_tokens`
2. **纳新自动带回**（`catalog.ModelInfo` 透传上游自愿给的字段）——xkiro 这条路是自动的
3. `/v1/models` 声明 `max_input_tokens` / `max_tokens` / `display_name`
4. **虚拟模型的窗口取候选里最小的那个**

### 为什么虚拟模型取 min

客户端拿 `auto:reasoning` 的窗口决定**何时压缩**。取 min 是"我能保证的下限"；
取首选或取 max 会把"我可能被换到更小的模型"藏起来，客户端压得不够早，
于是又撞回那个刚花大力气翻译的超限错误。
