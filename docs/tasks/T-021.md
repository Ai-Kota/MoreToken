# T-021: 90s 响应头超时杀掉了合法的大上下文请求

> 状态：**✅ 已修**（留痕 → 取证 → 按 body 大小缩放预算）。

**允许修改文件**：internal/**, main.go, docs/**

## 结论（2026-09-22 07:40 定案）

`ResponseHeaderTimeout = 90s` 是**常数**，而 **TTFT 是上下文的函数**。
实测（agnes，走真上游）：

| body | 响应时间 |
|---|---|
| 60 KB | 2.0s |
| 978 KB | 36.5s |
| **5.3 MB** | **80.8s** ← 距旧限制只差 9 秒 |

而失败的那批请求 body 是 **0.7–1.7 MB**，上游一忙就超过 90s ⇒ 被误杀。

**修法**：头预算改为 **per-request、按 body 缩放**：`90s + 60s/MB`。

| body | 旧 | 新 |
|---|---|---|
| 60 KB | 90s | 93.5s |
| 1 MB | 90s | **150s** |
| 1.7 MB | 90s | **192s** |
| 5.3 MB | 90s | **408s** |

小请求行为基本不变（+3.5s），大请求拿到与其真实耗时相称的余量。

## 实现要点

`ResponseHeaderTimeout` 是 **Transport 级常数**，一个 Transport 装不下两个值 ⇒
预算挪进 `provider.Invoke`，用 per-request 定时器（`context.WithCancel` + `AfterFunc`）实现。

**副产品**：失败原因从此能区分**两种含义相反的 canceled**：

| 现象 | 含义 |
|---|---|
| `transport: ... context canceled` | **调用方断开**（客户端不等了，与上游无关） |
| `header budget exceeded (budget=192s, body=1782579 bytes)` | **上游挂死**（我们的预算烧完） |

以前两者都是 `context canceled`——2026-09-21 排查时正是被这一点带偏过。

## 核心洞察（量化，但**未直接观测到**）

`internal/provider/transport.go`：

```go
DefaultResponseHeader = 90 * time.Second // 远大于 agnes 的 6–7s 首字节，不误伤慢模型
```

**这条理由只对 streaming 成立。**

| | 响应头的含义 |
|---|---|
| **流式** | 上游立刻回响应头，然后开始吐数据 ⇒ 响应头 ≈ 首字节 ✓ |
| **非流式** | 上游要把**整个回答生成完**才发响应头 ⇒ 响应头 = **整段生成时长** ✗ |

实测：**约 30ms / 输出 token** ⇒ **90 秒 ≈ 3000 输出 token**。
一条非流式请求只要生成超过约 3000 token 就会撞上它——**而它完全合法**。

这与本仓已修过的"22 万 token 硬墙"（T-010）是**同一类**：按错误假设定的限制，静默杀掉合法工作。

> **未坐实**：想用一条长输出去直接撞 90 秒，但模型不肯写那么长（两次只出 166/303 token）。
> 所以这是**量化推断，不是观测**——正是这一点决定了本轮只取证、不改策略。

## 本轮改了什么（只加留痕）

`router.Attempt` 补三个字段，让**下一次复发自证**：

| 字段 | 为什么是它 |
|---|---|
| `stream` | **排障时最大的障碍就是"不知道那条请求是不是流式"**——而这一个 bit 当时完全没记。它直接分开上面那张表的两行 |
| `elapsed_ms` | 撞 90s 头超时时会显示 ~90000，一眼可辨 |
| `body_bytes` | 排除"是不是大上下文把上游拖死"（本轮靠手工测量排除的，下次让日志自己说） |

**刻意没做**：不动 `ResponseHeaderTimeout`。改超时等于**同时改两处**（策略 + 留痕），
下次复发就分不清是修好了还是换了形态。
