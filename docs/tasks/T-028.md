# T-028: 代谢自动化——mt-deploy 变更检测 + 每日计划任务

> 起因：T-026 体检发现 A2 代谢断层（实证：harvest 12:44 更新宿主 models.auto.json，
> 容器卷内 config 是部署时快照，模型数 42 vs 54）——新纳模型进不了运行中的容器。
> T-027 重部署时即时闭合一次（42→54），但**下一次 harvest 后断层再现**。
> 用户批准方案 a：每日计划任务跑 mt-deploy（幂等）。

**允许修改文件**：docker/**, docs/**

## 设计

**问题**：mt-deploy 现在无条件 re-materialize + `compose up`。若每日定时跑：
- config 没变（多数日子，harvest 自节流 20h）→ `compose up` 不重建容器（镜像/配置未变）→ 零停机 ✓
- 但卷内 config.json 被**重新投递**（内容相同）→ 无害；内容变了 → 运行中容器**不会自动重读**
  （config 只在启动时 Load）→ 需要 restart 才生效。无条件 restart = 每天白断一次网关。

**修法（变更检测，restart 只在该restart时发生）**：
1. one-shot 投递容器里 `cmp -s config.json.new config.json`：相同 → 删 .new、stdout 打 `SAME`；
   不同 → mv 覆盖、打 `CHANGED`
2. mt-deploy 捕获标记：`CHANGED` 且容器在跑 → `docker restart moretoken` + 等 healthy；
   `SAME` → 不动容器（零停机）
3. 计划任务：每日 12:37（错峰整点）经 **wscript 隐藏宿主**跑 mt-deploy（对齐 dev-fleet
   run-hidden.vbs 的成熟形态——本机有"防弹黑窗"纪律，直接 schtasks 挂 bash 会闪窗）
4. 任务失效安全：mt-deploy 本身 `set -euo pipefail` + 幂等；失败不影响运行中容器
   （.new+cmp+mv 原子语义：投递失败现役 config 不动）

**边界**：上游 key 轮换（vault 值变）同样被变更检测捕获（materialize 输出不同 → CHANGED
→ restart）——每日任务顺带成为 key 轮换的自动收敛点（最迟 24h 生效）。

## 实测教训（两处 exit 1 → 修正）

1. **动作内嵌引号被包装搞坏**：`/tr "\"D:\…bash.exe\" \"E:\…sh\""` → flashcheck 包成
   `hidden-run.vbs ""D:\…bash.exe"" …`（双引号畸形）→ exit 1。修正：路径无空格 → **动作不带引号**
2. **Task Scheduler 环境裸**：`dirname $BASH_SOURCE` 不认 Windows 反斜杠 → cd 错目录 → exit 1。
   修正：mt-deploy-logged.sh **硬编码仓库根**（POSIX+Windows 双形态兜底）+ 显式 `export PATH=/usr/bin:/bin:$PATH`
   （调度器环境没有 MSYS 工具链）。不依赖任何继承环境。
