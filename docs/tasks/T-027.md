# T-027: 修流式请求错误路径——首块前不发 200，状态码回归真实

> 起因：2026-09-29 T-026 部署后体检，容器日志 13:06:39 起连续出现
> `http: superfluous response.WriteHeader call … chatHandler (proxy.go:307)`——
> 10 分钟内 3 次，全部来自**用户真实 cc-ft 会话**（决策日志同期可见 laptop-cc 的
> auto:reasoning 流式 200 大负载请求）。307 行正是 400 上下文超限路径。

**允许修改文件**：internal/**, docs/**, docker/**

## 缺陷机制（代码实锤，非推断）

`chatHandler` 对 streaming 请求在 `Route()` **之前**就设置 SSE 头并 `Flush()`
（proxy.go:230-238）——flush 即把 **200 + text/event-stream 头送上 wire**。
之后三条路由错误路径（404 模型不存在 / 400 上下文超限 / 503 池耗尽）调
`http.Error(w, msg, status)` → WriteHeader 已迟 → Go 记 superfluous、
**真实状态码到不了客户端**。客户端（Claude Code，100% 流式）收到的是
`200 + SSE 头 + 一坨裸错误 JSON`。

**后果**：T-023 的全部错误语义在流式路径失效——
- `400 prompt is too long: N > M` → 客户端本应提示 **/compact**，实收破碎流
- `404 not_found_error model: …` → 本应提示 **/model 换一个**，实收破碎流
- `503 exhausted` → 本应触发重试语义，实收破碎流

定性：**T-003/T-010 时代老伤，非容器化引入**；容器日志（带外记录）首次让它现形。

## 修复边界（为什么干净）

流式语义已核实（provider.go:326/385-395、router.go:300-307/485-486）：
- 上游 ≥400 在**流开始前**就转 Fail → 走 I7 重试或上抛 ferr
- **流中断（FailStreamMid）走 `done=true` 以 ferr==nil 返回**（成功路径），不经 http.Error
- ⟹ **ferr != nil ⟹ 零数据块已发出**——把首次 flush 推迟到第一个 StreamCB 数据块，
  三条错误路径自动恢复真实状态码，无边界纠缠

## 改动（一处，proxy.go chatHandler）

1. 删掉 Route 前的 SSE 头设置 + flush
2. StreamCB 首块时设 SSE 头（三行 Set）+ 置 `streamStarted=true`，随后写块 + flush（既有逻辑）
3. 流式成功路径：`if !streamStarted { w.WriteHeader(res.StatusCode) }`（空流=上游 200 零块，
   显式给状态码，不靠 Go 隐式 200）
4. 错误路径**一行不动**（http.Error 从此生效）

**为什么早 flush 当初不构成价值**：路由期间客户端等事件，60s 流空闲计时照跑
（早发头不产生事件）；删除后成功路径 wire 行为不变（头随首块发出），
错误路径从"破碎流"变"真实状态码"。纯改善，无权衡。
