# T-049: anthropic/coding 偶发 503 —— 供给单点 + 准入表清空（待定策）

> 定案：走“稳定现有第二供给”路线——不新增 provider/未测模型、不降低 0.8 门槛。
> 来源：2026-10-25 容器体检。NATS metrics 显示 60 分钟窗口
> `anthropic/coding: total=12, fail=9`，随后用 `/decisions`（1024 条环）定位。

## 已核实证据

- 08:14–12:21 的 1024 条决策中，`auto:coding` 共 42 条：32 成功、**10 条 503**，
  全部 `auth=cc-mt`；失败集中在 11:08–11:39（每 12–30 秒一组，共 10 次）。
- 503 的 attempts（逐候选留痕）：

  | provider | 结果 |
  |---|---|
  | `agnes-anthropic` | `provider agnes-anthropic has no model of kind "coding"`（9 次）|
  | `xkiro-anthropic` | `model rotation exhausted`（9 次，elapsed ≈ 14.9s）|
  | `openrouter-anthropic` | `provider openrouter-anthropic has no model of kind "coding"`（10 次）|

- 失败的 399 秒窗口结束后（11:54 起），同一条 `auto:coding` 改由
  `agnes-2.5-flash` 成功——说明不是网络全断，而是**候选集短时为空**。
- 08:17–10:53 的 `auto:coding` 成功请求全部落到 **`agnes-3.0-flash`**（32 次）。
  该模型已在 T-043 中剔出免费池（2026-10-25 部署）。

## 机制（已核实部分）

1. `ResolveModels` 先按 `model.Kinds` 取该 provider 的 coding 候选；
   `filterByAdmission` 再用准入表**严格过滤**（`Admission.Admitted`）。
   agnes-anthropic 的手写模型 2.5-flash 带 coding kind，但若准入表里它当轮
   没有 coding 通过行，候选会被清空 ⇒ 报“没有该 kind 的模型”。
   因此这条 reason 的真实含义是 **“准入过滤后为空”**，不是“配置里没这个 kind”。
2. xkiro-anthropic 的 `model rotation exhausted` 只说明池内模型/ key 轮换耗尽；
   attempts 里没有记录每把 key 的 429/失败码 ⇒ **具体是额度墙还是全 key 冷却，【未核实】**。
3. openrouter-anthropic 当前确实没有任何 coding 模型——这条是静态覆盖缺口。
4. 准入表由评测器每 30 分钟一轮热加载，**coding 资格会随轮次波动**：
   同一 provider 在 11:08 无 coding 候选、11:42 表更新后 11:54 恢复。

## 影响

`auto:coding` 在 anthropic 协议路径上实际只有 **1 个有效供给点**（agnes-anthropic
的 2.5-flash）在大部分时间可用；它一旦被准入表临时清空或上游限流，
xkiro 若同时轮换耗尽、openrouter 无 coding 模型，就直接 503。
这不是网关 bug，而是**供给冗余不足 + 准入波动被直接暴露为请求失败**。

## 待定策（不要在本档直接改代码）

- a. 补供给：让 xkiro / openrouter 至少再稳定提供 1 个 coding 模型
      （需实测 + 写入 admission，不能只靠 models.auto 的 general）；
- b. 准入清空时的降级策略：某 provider 的 coding 候选被过滤为空时，
      是否回退到 kinds 候选（并在 /decisions 明示 `admission_fallback`）；
      这是行为变化，需用户定夺；
- c. 诊断文案：把 `has no model of kind` 改为能区分“配置没有”与“准入过滤光”
      （后者是 2026-10-25 现场最容易误判的一层）。
- 另：xkiro 的轮换耗尽原因需在 attempts 里补每把 key 的结果码才能定论。

## 定案（2026-10-25）

**决定：稳定现有第二供给，不补新 provider、不降准入门槛。**

### 证据

- 网关过滤器**没有 bug**：`Admitted` 使用 `minRatio`（0.8，含浮点容差），
  agnes-2.5-flash 的 coding 4/5 在 0.8 线下是通过的。
- 当前表：`agnes-2.5-flash coding 4/5`、`sensenova 5/5`、`qwen-plus 4/5`；
  但快照里 admission coding 数在 **17:44=2 → 17:46=3** 波动，随表更新变化。
- `ops/dev-fleet/sync-admission.ps1` 明确写着 **“newer rows win per model”**：
  单轮 3/5 会覆盖此前的 4/5。16:11–16:43 的 7 次 `admission_empty` 就是
  这种覆盖造成的——不是“没有合格模型”。
- 16:18:38 的唯一真实 503 是休眠过渡期容器 DNS 失败（agnes/xkiro 同时
  `127.0.0.11 no such host`），与 coding 供给无关。

### 实施

1. **`ops/dev-fleet/sync-admission.ps1`（跨项目）**：按模型/维度做
   **best-of-window（3 小时）** 合并：
   - 旧行只在 `checked_at` 处于 3 小时窗口内、且该维度通过率更高时保留；
   - 窗口外的旧证据自动淘汰（不允许无限期掩盖真实退化）；
   - 新旧行的 `battery_verdict` 均合法（PASS/FAIL/UNCERTAIN），合并行取
     保留维度的来源行，`checked_at` 取较新者。
2. **`scripts/mt-report.py`**：新增 `coding_supply` 摘要（coding 请求数、
   各 provider 的 `admission_empty` 次数、最终服务 provider、失败数）。
3. **不改网关路由/准入线**；网关只消费更稳定的表。

### 验收

- 24 小时内 coding 的 `admission_empty` 显著下降；agnes 的 4/5 在窗口内不再被
  单轮 3/5 打掉。
- coding 请求至少由 agnes/xkiro 两家可服务；两家都不可用才允许 503。
- 若稳定后仍出现 coding **实际失败**（不是 wasted attempt），再升级为
  “补第二 provider（openrouter，需先让评测器覆盖该 base 并产出 coding 证据）”。
