# T-018: 免费池的新陈代谢（发现 → 实测 → 入库）

> 起因（用户定性）：**需要有一个机制来保证有源源不断的优质大模型进入池中。这种新陈代谢才是真正的良性循环。**
> 并纠正了我的漏判：我在 T-016 的 §7.3 说"上游悄悄撤模型不需要额外机制"——
> 只算了**发现时延**（有界），漏算了**恢复时间常数**：模型没了，补回来要
> "人去找 → 验证 → 改配置 → 部署"，**无界**。按停止规则它恰恰合格。

**允许修改文件**：internal/**, main.go, docs/**, ../../ops/dev-fleet/staleness*.go, ../../ops/dev-fleet/services.yaml

## 一个前置阻断项（不修它，纳新等于装饰）

建 harvester 前先验了一件事：**纳进来的模型路由用不用得上**。答案是用不上——

`tryCandidate` 在 key 循环**之前**解析一次模型，然后只用它轮 3 把 key，
同 provider 的其余模型永远不会被尝试。实测：带一个可用备用模型的 provider，
首选 5xx 时请求整体失败（`router: exhausted anthropic candidates (tried 1, limit 4)`）。

**池子的维度是 (provider × key)，模型维度是死的** ⇒ 加 24 个模型净收益 0。
已先修（模型轮换），见提交 `68f9b06`。

## 机制

```
发现（拉 /v1/models）→ 实测（真调一次，2xx 才算）→ 入库（models.auto.json）→ 加载（config.Load 合并）
```

复核与淘汰**不新增机制**：交给运行时的模型轮换承担（上游撤了模型就回 404，
路由同 provider 换下一个），比离线定时复核更及时。

### 四条硬规矩

| 规矩 | 为什么 |
|---|---|
| **列表 ≠ 可用，必须真调** | 抽样实测：4 个里 1 个上游 500。T-011 的教训第二次成立 |
| **kinds 只给 `general`，且写成结构约束** | 实测能证明"它活着"，证明不了"它会推理"。要升格必须人工实测后写进手写区 |
| **只追加，排在所有手写模型之后** | 一次纳新不该有权把主力模型换掉 |
| **清单累积，不每轮重建** | 见下——这条是第二轮真跑才暴露的 |

## 真跑暴露的三个问题（都已修）

1. **Max 被旗舰模型吃光**。目录把旗舰排在前面，而旗舰对这一档凭据**全部 403**：
   第一轮 Max=6 时六个候选全 403，27 个真正可用的 `:free` 一个没轮到。
   ⇒ 修：`:free` 标记**优先实测**（上游自己的声明当先验，是排序不是过滤）。

2. **清单每轮重建 ⇒ 自我侵蚀**。第二轮 agnes 的 `verified` 变成空——
   上一轮验过的 `agnes-3.0-flash` 这轮因已并进 config 被当 `Known` 跳过，覆盖写就把它抹了，
   下次加载不再并进 config。**正好是"源源不断"的反面**。
   ⇒ 修：先读旧清单、继承已验模型，只做加法。

3. **403 的文案在撒谎**。复用 provider 的口径写成"凭据被拒，隔离该 key"，
   而实测同一把 key 对 `agnes-2.5-flash` 回 200、对 `agnes-2.5-pro` 回 403——
   凭据是好的，是账号对这个模型没权限。⇒ 修：纳新用自己的措辞，且**不惩罚任何 key**。

## 遗留

1. **未做"离线复核/淘汰"**：已验模型若上游撤了，靠运行时 404 → 模型轮换兜住。
   够用，但清单里会留下永远不再被选中的死条目（不影响正确性）。
2. **`403` 在路由侧的语义可疑**（本任务新发现，**未修**）：
   `provider.Invoke` 把 403 归为 `FailAuth` → 路由会 `RecordDead(key)` **长禁该 key 1 小时**。
   但本任务实测证明 403 常常是"账号对这个模型没权限"，同一把 key 对别的模型可用。
   ⇒ 一个账号无权的模型若进了 config，会**把该 provider 的 key 全部长禁 1 小时**，
   连带整个 provider 下线。今天是潜伏的（config 里没有这种模型），
   但纳新**正好会把这类模型摆在眼前**，人工一顺手加进去就中招。
   建议：403 先按模型级处理（换模型），401 才按凭据级（换 key）。
