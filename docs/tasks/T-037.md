# T-037: 平台发现 —— 注册表 × vault × config 三向 diff

> 用户定性（2026-10-05）：**"发现新平台的任务要做；你发现新的平台之后，我会去注册更多的 apikey。"**

**允许修改文件**：config/platforms.known.json, internal/platform/**, main.go, docs/**
**允许新增文件目录**：internal/platform/, docs/

## 问题（T-033/036 暴露的真根）

`catalog.Harvester` 只对 **`cfg.Providers` 里已声明的 provider** 发现新**模型**——
`for i := range cfg.Providers`。**它永远不会发现一个新"平台"。**
于是池子的大小由人手写的一份 provider 列表定死（当前 7 个），vault 里有多少平台都白搭。

## 交付

**三向 diff**，回答"我们还缺哪些平台"：

| 桶 | 判据 | 动作 |
|---|---|---|
| ✅ 已接线 | 注册表 ∩ config（按 base_url 主机名匹配） | 无 |
| ⚠️ 有 key 未接线 | vault `freellm/provider/*` ∩ 注册表 − 已接线 | 可直接接（跑能力测试后准入） |
| 🆕 **已知但无 key** | 注册表 − vault − 已接线 | **用户去注册**（这就是用户要的清单） |

**注册表**：`config/platforms.known.json`。种子来自 freellmapi 的平台注册表
（`another/FreeToken/freellmapi/server/src/providers/index.ts`，~30 个平台含 base_url），
外加 openrouter / cloudflare 等。

**命令**：`moretoken -platforms`（与 `-check` 同级的只读子命令）。

## 验收

- [ ] `-platforms` 输出三桶，且**未接线的有 key 平台**（unorouter/orcarouter/cloudflare/qwen）被正确列出。
- [ ] 纯函数 diff 有单测（三桶边界：注册表有/无 × vault 有/无 × config 有/无）。
- [ ] 不改任何路由行为。

## 不做

- 自动接线（接线要过能力测试，见 T-036 的规矩）。
- 联网发现（注册表是人工/种子维护；"发现"= 与现有凭据对账）。
