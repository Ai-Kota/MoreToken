# 模型能力实测证据（virtual model 的 kinds 依据）

> 这份文档存在的理由：`kinds` 决定 `auto:<type>` 把请求路由给谁。
> 如果 kinds 是"按印象填的"，那类型路由就是**建立在猜测上的确定性**——比不做更糟，
> 因为它让一个错的假设披上了架构的外衣。
>
> 本文件记录 2026-09-19 的实测过程与原始数据，供下次换模型时对照重跑。

## 一、方法

探针经**本网关**发出（Go net/http），避开本机 Git Bash + schannel 对 agnes 的间歇性
TLS 失败（那个会产出假的 `HTTP=000`，污染结果）。每个探针**跑多样本**。

### 为什么必须多样本

单样本会给出**自相矛盾的结论**。同一模型同一题，两次跑结果不同：

| 模型 | 题 | 第 1 次 | 第 2 次 |
|------|----|--------|--------|
| agnes-2.5-flash | 3/5 倍数求和 | 判错（解析原因） | **答对 `233168`** |
| agnes-2.0-flash | 火车追及（8 样本） | 7/8 | **3/10**（10 样本复测） |

LLM 有采样方差。**单次通过的探针不构成能力声明**——这正是不能"跑一发就填 kinds"的原因。

### 探针题（可判定，有唯一正确答案）

| 类别 | 题 | 正确答案 |
|------|----|---------|
| reasoning | 火车 14:35 以 80km/h 出发，第二列 15:05 以 100km/h 同轨同向，何时追上 | `17:05` |

## 三、结论

1. **`coding` 与 `general` 不区分。** 所有模型在这两类题上 88–100%。
   把它们当作"区分性类型"是**虚假精度**。现声明为**普遍能力**——诚实，但不产生路由差异
   （即 `auto:coding` 与 `auto` 等价）。这一点必须写下来，否则下一个人会以为
   `auto:coding` 挑出了更会写代码的模型。

2. **`reasoning` 真的区分，但只有极端值可信。**
   `agnes-2.5-flash` 10/10 是明确信号；`0/10` 那组也是明确信号。
   中间区（`minimax-m3` 6/10、`agnes-2.0-flash` 3/10→7/8 大幅漂移）**不足以支撑强声明**，
   收录 `minimax-m3` 是因为 6/10 与 0/10 的差距仍显著，且它给 `auto:reasoning`
   提供了第二个候选（单一候选等于没有 failover）。

3. **`fast` 只有 agnes 三模型有实测**（0.9 / 1.0 / 1.9s）。
   xkiro 三个模型在实测期间返回 503（原因见下），**未测到延迟，故不声明 `fast`**。
   宁可少标，不可猜标。

4. **一个反直觉结果**：付费的 `agnes-3.0-flash` 推理得分最差（0/10），却最快（1.9s）。
   它不是"更强的模型"，是**不做长推理的快速模型**。这也解释了为什么它适合当 `fast`
   而不是 `reasoning`——旧的 kinds 标注把它当通用强模型是错的。

### xkiro 模型 503 的原因（不是缺陷）

实测期间对 6 个模型并发打分（120 请求 / 25 秒，另有 70 请求的延迟测量），
超过池容量：agnes 免费档 **20 RPM/账号且按账号隔离**，33 把 key ≈ 660 RPM 上限，
而峰值打到约 720 RPM。于是 33 把 key 里 28 把进了 429 冷却、xkiro 11 把全冷却。

**观察到的正确行为**：
- 免费全挂时状态机触发 `all-free-unavailable` 事件、切付费层，付费 key 顶上并返回 200
- 冷却 60s 后自动恢复（复测时 agnes cooling 归 0）
- 期间返回 503 而不是错误地把请求透传成 401

**暴露的短板**：付费层只有 1 把 key，同样会被打冷却。持续高并发时付费兜底也会耗尽——
兜底是"保命"不是"扩容"。
