# 紧急协议（破玻璃机制）

> **当正常流程无法解决问题，或约束本身成为阻碍时，启用本协议。**
> **必须事后复盘，记录原因，更新约束。**

---

## 一、什么情况下启用

| 场景 | 是否适用 | 替代方案 |
|------|:--------:|---------|
| 生产环境紧急修复 | ✅ | 正常流程太慢，问题在扩散 |
| 约束导致阻塞（误判） | ✅ | Hook 误拦截，无法正常工作 |
| 安全事件紧急响应 | ✅ | 需要立即删除/隔离 |
| 约束本身有 Bug | ✅ | 无法绕过，影响开发 |
| 正常决策流程太慢 | ⚠️ | 人工审批延迟超过 2 小时 |

---

## 二、紧急操作权限

启用紧急协议后，AI 被授予以下临时权限：

| 操作 | 正常权限 | 紧急权限 | 事后要求 |
|------|---------|---------|---------|
| 修改配置文件 | L4 需报告 | **L2 可自主** | 1 小时内补报告 |
| 新增依赖 | L5 禁止 | **L4 需报告** | 24 小时内补 CR |
| 修改 CI 配置 | L4 禁止 | **L2 可自主** | 2 小时内补审批 |
| 修改文件范围 >5 个 | X5 禁止 | **允许但需记录** | 1 小时内补说明 |
| 跳过设计文档 | R2 禁止 | **允许但需记录** | 24 小时内补设计 |
| 跳过测试 | R3 禁止 | **允许但需记录** | 立即补测试 |

## 三、启用流程

```
1. AI 识别到需要紧急处理的情况
    ↓
2. 在 SESSION-STATE.md 记录：
   - 紧急原因
   - 紧急操作内容
   - 预期修复时间
   - 事后补全计划
    ↓
3. 执行紧急操作
    ↓
4. 1小时内：补全记录（SESSION-STATE.md）
    ↓
5. 24小时内：补全审批/文档/测试
    ↓
6. 48小时内：完成根因分析和约束更新
```

## 四、紧急操作记录模板

```markdown
### 紧急操作记录 - [时间]

| 字段 | 值 |
|------|-----|
| **紧急原因** | [为什么需要紧急处理] |
| **紧急操作** | [具体做了什么] |
| **涉及文件** | [文件列表] |
| **预期影响** | [对系统/用户的影响] |
| **事后补全计划** | [何时补什么] |
| **状态** | 🔄 执行中 / ⏳ 等待补全 / ✅ 已完成 |
```

## 五、事后复盘要求

紧急操作完成后，必须进行复盘：

### 5.1 复盘内容

1. **触发原因**：为什么正常流程不适用？
2. **约束缺陷**：是约束太严？还是约束本身有 Bug？
3. **改进建议**：如何修改约束，避免下次再需要紧急处理？
4. **权限调整**：是否需要永久调整权限级别？

### 5.2 复盘输出

- 更新对应约束文档（如果约束需要调整）
- 更新 VIOLATION-HANDLING.md（如果违规处理流程有改进）
- 记录到风险登记册（如果是新风险）
- 通知相关方（如果影响范围大）

---

## 六、约束更新决策树

```
紧急操作完成
    ↓
约束是否合理？
├── 是 → 保持约束，记录为新风险
└── 否 → 约束需要调整
         ├── 过严 → 降低约束级别（如 L5→L4）
         └── 过松 → 提高约束级别（如 L1→L2）
    ↓
更新文档
    ↓
通知相关方
    ↓
完成
```
