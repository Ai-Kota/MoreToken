# 违规处理协议

> **核心原则：违规必须被捕获、记录、处理、恢复。不允许"算了"。**

---

## 一、违规分级

| 级别 | 定义 | 示例 | 处理时效 |
|:----:|------|------|:--------:|
| **V1** | 轻微违规（可自动恢复） | 文档未同步、任务状态未更新 | 立即修复 |
| **V2** | 中度违规（需记录） | 范围越界（<5 文件）、未验证外部引用 | 本次会话内修复 |
| **V3** | 严重违规（需人工介入） | 编造 API/函数、越权修改架构/部署配置 | 停止执行，等人工决策 |
| **V4** | 危险违规（需升级） | 删除文件、修改生产配置、密钥泄露 | 立即停止，紧急处理 |

---

## 二、违规捕获机制

| 捕获点 | 机制 | 覆盖违规 |
|--------|------|---------|
| **Pre-Write Hook** | read_tracker.json 检查 | R1 先读后写 |
| **Pre-Write Hook** | 设计文档存在性检查 | R2 先设计后编码 |
| **verify-task.sh/py** | 全自动门禁 | R3 测试通过、安全扫描 |
| **post-code-check.sh** | 符号存在性检查 | X7 反幻觉 |
| **人工 Review** | 代码审查 | X3-X6 等逻辑类约束 |

---

## 三、违规处理流程

```
检测到违规
    ↓
1. 记录到 SESSION-STATE.md "待决策项"
   - 违规级别
   - 违规描述
   - 影响范围
   - 建议修复方案
    ↓
2. 根据级别处理
   V1 → 立即修复，记录日志
   V2 → 回滚代码，修复后重试
   V3 → 停止执行，等人工决策
   V4 → 立即停止，紧急上报
    ↓
3. 修复验证
   - V1/V2: 重新运行 verify-task.sh
   - V3: 人工审批通过后继续
   - V4: 紧急处理完成后全面审查
    ↓
4. 根因分析
   - 违规原因
   - 为什么没被提前预防
   - 如何改进约束/流程
    ↓
5. 更新约束文档（如需）
   - 补充拦截规则
   - 增加检查项
```

## 四、违规恢复操作

### V1/V2: 自动恢复

```bash
# 回滚文件修改
git checkout -- <file>

# 回滚整个任务的修改（危险）
git stash
```

### V3: 人工介入后恢复

1. AI 记录违规详情到 SESSION-STATE.md
2. 人工审查违规内容
3. 人工决策：
   - 批准：AI 按人工指示继续
   - 拒绝：AI 回滚并寻找替代方案
   - 修改：AI 按修改后的方案重新执行

### V4: 紧急恢复

```bash
# 紧急回滚
git stash
# 或
git reset --hard HEAD~1  # ⚠️ 仅限维护者操作

# 通知相关方
# 记录事件报告
# 启动复盘
```

## 五、申诉机制

AI 认为约束本身有问题时：

```
AI 记录申诉到 SESSION-STATE.md
    ↓
1. 申诉内容
   - 哪条约束导致问题
   - 约束的预期目的
   - 实际遇到的情况
   - 建议的约束修改
    ↓
2. 人工评估
   - 约束是否合理
   - 是否需要调整
    ↓
3. 决策
   - 维持原约束：AI 必须遵守
   - 调整约束：更新对应文档 + 通知相关方
   - 废弃约束：记录废弃原因，更新文档
```

## 六、重复违规升级

| 模式 | 触发条件 | 升级处理 |
|------|---------|---------|
| 同类违规 3 次/周 | 相同类型违规反复发生 | 升级 1 级处理 |
| 同一任务 2 次违规 | 同一任务多次违规 | 暂停该任务，等人工评估 |
| 违规频率上升 | 周违规次数 > 前一周 | AI 权限降级（收回 L2 自主权） |
